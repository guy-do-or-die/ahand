# The app

```
/31337/14?d=AgFP…#<link>   →   the fragment is read once into memory, then removed from the address bar
                               the Deal card: "Someone raised a hand:" over the title "a sublet in Yerevan, June."
                               [🤝 Pass it on]   [🙌 I can help]
```

`apps/hand`: React 19, Vite 8, wagmi 3 (EIP-6963 injected wallets, and logging in through Privy when the configuration has `privy`; see "Logging in through Privy" below), a 60-line router over `pathname` (`src/router.ts`, one table in `src/routes.ts`). The build is a folder of static files plus a self-contained `exit.html`. English and Russian; Russian speaks as «ты». Built with `bun run --cwd apps/hand build`; unit tests `cd apps/hand && bun test`; browser smokes `tests/e2e/smoke/*.spec.ts`.

## What the device stores

The link's 16-byte seed lives in the address its holder was sent and in the memory of the tab that opened it (`src/store/memory.ts`); a reload forgets it, and the screen says so. IndexedDB database `ahand` (`src/store/db.ts`):

| Store | Holds | A secret? |
|---|---|---|
| `books` | the 8-byte book per asker; whether the account repeats its signatures | no |
| `hands` | my Hands: chain, Core, number, `n`, the raise intent and hash, mode, the words and salt | the asker's own words; no key |
| `inbox` | answers received or pasted, as give links (no secret by format), first-seen time on this device, routes seen | no |
| `outbox` | the helper's give links, delivery status, the per-answer chat key | a chat key only |
| `passed` | Hands passed from this device: chain, number, position, payee | no |
| `prefs` | language, lens, theme; in a build with Privy, the raise form while a social login leaves the page and comes back (`raiseForm`, at most 30 minutes, below) | the asker's own words; no key, no link |
| `vault` | one AES-GCM key per device, created non-extractable | cannot be read out |
| `escrow` | **the locked copy**: for an account whose signatures do not repeat, the new Hand's seed encrypted under the vault key, written before `raise` is sent, deleted when the asker ticks "I saved the link" or the raise is found reverted, and by the sweep on every start (below) | yes, encrypted, at most one day after the link is shown |

The locked copy (`lockSeed`, `openSeed`, `dropSeed`) binds the raise intent as AES-GCM associated data with a fresh IV. It protects against a storage dump and a crash, not against this site's own code. It is a recorded deviation (D-63). Each copy carries two chain times (`stampSeed`): when the raise read the chain, and when the "up" screen first showed the link. On every start the app sweeps them (`apps/hand/src/screens/raise/sweep.ts`, by the chain's clock, never the device's): a copy is deleted once its Hand is closed or past its end, one day (`SHOWN_BOUND`, 24 h) after its link was first shown, when its raise reverted, or when no raise on the device names it; a copy whose raise is still on its way, or whose Hand cannot be read now, is kept. Until then `/my` says the link is kept locked on this device. Tests: `apps/hand/src/screens/raise/sweep.test.ts` and `apps/hand/tests/guards/store.test.ts` (no seed in any store in any form; the vault key not exportable). The theme toggle also writes one `localStorage` key, `ahand-theme`.

Clearing the storage loses only "My hands on this device", answers seen and the outbox; every flow still works from a link.

## What is logged

- **The app**: nothing leaves the device. No `console` call in `src`, no `sessionStorage` but the one key that carries an opened link across a social login's reload (`link-carry.ts`, question 11 in [defaults.md](defaults.md)), no cookies, no analytics, no service worker. React's error hooks are no-ops so an error carrying link text never reaches the console. Guards: `apps/hand/tests/guards/secrets.test.ts`; `tests/e2e/guards/hygiene.spec.ts` searches every request, console line and storage entry of a run for the seed as hex, base64url and decimal digits.
- **Face** (`apps/face`) and **`infra/stand/static.ts`**: method, path without the query, status. Never a fragment, never `d`.
- **The stand's relay** (`infra/relay/relay.ts`): counts only (stored, accepted, rejected, clients).

## Headers

Face and `static.ts` send `Content-Security-Policy: default-src 'self'; script-src 'self'; … connect-src 'self' <rpc> <relay>; frame-ancestors 'none'` and `Referrer-Policy: no-referrer` (`apps/face/src/headers.ts`). `exit.html` alone also allows any RPC the reader types, and the hash of its one inline script. No third-party script from another origin.

A build whose configuration has `privy` adds what Privy's [Content Security Policy page](https://docs.privy.io/security/implementation-guide/content-security-policy) (read 2026-11-21) lists for the ways in this app offers, and nothing else (`apps/hand/csp.ts` `PRIVY_CSP`, the same in face's `PRIVY_SOURCES`, `FACE_PRIVY=1`):

- `frame-src` and `child-src`: `https://auth.privy.io` (Privy's login and key frame), `https://verify.walletconnect.com` and its fallback `https://verify.walletconnect.org` (WalletConnect's verify frame);
- `connect-src`: `https://auth.privy.io` (Privy's API), `https://*.rpc.privy.systems` (the RPC Privy's wallets send through), `wss://relay.walletconnect.com` and `wss://relay.walletconnect.org` (WalletConnect's relay, for a phone app), `wss://www.walletlink.org` (Coinbase's relay, which the page lists among the required domains of `@privy-io/react-auth`), `https://explorer-api.walletconnect.com` (WalletConnect's list of wallets);
- `img-src`: `https://explorer-api.walletconnect.com`, the icons of that list (Privy's page keeps `img-src 'self' data: blob:` and lists no image host; the icons come from there, seen on the built page, so they are named).

Where the app's policy differs from Privy's page on purpose: `img-src` has no `blob:` (in Privy's 3.51.3 code only the wallet-password form, which this app does not use, and the cards kit make `blob:` URLs), `worker-src` stays `'none'` where Privy's page has `'self'` (Privy's code on the page starts no worker), and `form-action` stays `'none'` where Privy's page has `'self'` (no form here posts anywhere). Privy's own frame on `auth.privy.io` runs under Privy's own policy, which the page's does not govern. Not yet seen under a real login: the email code screen, a passkey, Farcaster and the signing of Privy's own wallet. On the first real round, keep a `securitypolicyviolation` listener on (`document.addEventListener("securitypolicyviolation", …)` in the browser's console) and add what is missing, by name.

Left out of Privy's list: Cloudflare's `script-src`/`frame-src` (Privy's bot protection stays off; turning it on in the dashboard needs a third-party script, which ARCHITECTURE §11 does not allow), Telegram, the funding kit and Solana. `script-src` stays `'self'`: Privy's code ships in the app's own files. `exit.html` never gets any of it. Measured on a Base Sepolia build served at `http://localhost:3411` (2026-11-21, after Google, Apple and X were offered everywhere and Coinbase's relay was added): Privy's window opened six times (three from "Raise your hand", three from "Log in"; English and Russian, light and dark, 1440 and 390 px), its wallet screen three times and Rainbow's WalletConnect code once, with no CSP violation on the page and no page error; Privy's own frame on `auth.privy.io` reports its own violations to Datadog under its own policy, which the page's policy does not govern.

## Logging in through Privy

Decided by the owner on 2026-11-21: one way in through Privy, with email, social accounts and wallets in the same window. So where the configuration has `privy` there is one way in, Privy's own window, and nothing of the app's comes before it:

- The control is "Log in" («Войти»). It, and every action that needs an account (the raise swipe, "Log in to get paid" on /give and /pass, Deliver on /waiting, the thanks, the refund, the withdrawal), opens Privy's window directly (`apps/hand/src/wallet/ConnectSheet.tsx` `PrivyLogin`). The window offers an email field, Google, X, "Other socials" (Apple, Farcaster), "Continue with a wallet" and "I have a passkey". "Continue with a wallet" lists the wallets this browser announces (EIP-6963: MetaMask, Rabby, Coinbase Wallet's extension and others), then MetaMask, Rainbow, Zerion and Uniswap by name, then WalletConnect's list for every other phone app (602 wallets on 2026-11-21). Which ways in Privy offers and how each is turned on: Privy's [login methods](https://docs.privy.io/authentication/user-authentication/login-methods/oauth) pages. The first time on a page, while Privy's code loads (1.8 to 2.8 s measured locally), a line at the bottom says "Opening log in…" («Открываем вход…»); while Privy's window is open the app shows nothing of its own.
- Google, Apple and X are offered on every screen, as the owner asked. They leave the page: Privy's SDK sends the browser to the provider (`window.location.assign`; Privy 3.51.3 has no pop-up for them) and the provider sends it back to the same address with `privy_oauth_code`; Privy then loads at once and the person is let in. A fresh load forgets what the page holds only in memory:
  - the raise form: when the swipe asks someone to log in, the form (the words, the reward, the days, the mode, the shares) is written to `prefs` as `raiseForm`, removed however the login ends on the page, and taken out as /raise opens, filled back in only if it was written within 30 minutes (`apps/hand/src/screens/raise/kept.ts`). The asker's own words, which `hands` keeps anyway once raised; no seed, no key, no link. Then the swipe again goes on logged in.
  - an opened link: carried across that one trip, the one exception to D-39, decided by the owner on 2026-11-21 (question 11 in [defaults.md](defaults.md), option b). While Privy's window is open on the Hand view with a link, /give or /pass, the page leaving (`pagehide`; Privy itself starts the redirect, so that is the narrowest moment the app sees) writes the link, as memory held it, with the path and the device's time, to this tab's `sessionStorage` under `ahand-link-carry` (`apps/hand/src/link-carry.ts`, armed by `openLogin` in `wallet/privy-host.tsx`). The key is erased when the login ends on the page, when the page comes back from the back-forward cache, and on every load right after link intake (`main.tsx`), before use; it is put back into memory (never into the address bar, whose query then holds Privy's one-time code) only on the way back from a social login, on the same path, within ten minutes, and when the address brought no link of its own. Storage that refuses carries nothing: the person opens the link once more, and "You're logged in. … open the one you were sent once more." (`LinkAgain`) still says so. For later, not built: the owner's idea of a setting of the person's own, kept encrypted in ENS data records.
- A login that Privy answers with an error (other than the window being closed), or whose wallet never appears, ends with one line at the bottom, "Logging in didn't finish. Nothing was sent." with "Try again" (opens Privy's window again) and "Close"; never the app's own sheet. Only Privy unreachable brings the app's own sheet, below.
- The account is the wallet the person logged in with: a wallet Privy makes and keeps (`createOnLogin: users-without-wallets`, its key inside Privy's frame on `auth.privy.io`) for email, social accounts and passkeys; the crypto wallet itself for a wallet login (Privy asks it for a sign-in message first). In the app it is one wagmi connector (`apps/hand/src/wallet/privy.ts`) over that wallet's EIP-1193 provider, so raise (approve, then raise, as two steps: Privy's wallet has no EIP-5792 batch), give and shake signatures (`eth_signTypedData_v4`), thanks, refunds, withdrawals and the switch to chain 84532 take the same path as before. No `@privy-io/wagmi`: the wallet layer has no React providers to adapt.
- The network: Privy's own wallet moves to Base Sepolia at once; a crypto wallet is asked to (its own window, Privy adds the chain if the wallet lacks it). If the person says no, it stays connected on its own chain and the screens' own "switch to Base Sepolia" step takes over, as for any wallet.
- Logged in, the control shows "Logged in: 0x12…34" («Вход выполнен») and "Log out" («Выйти»), which ends the Privy session on this device. Another account is "Log out", then "Log in".
- Staying logged in: on login the app writes one word, `"1"`, under the key `ahand-privy` in localStorage (`wallet/privy-mark.ts`, wrapped in try/catch; the secrets guard allows this key and the theme's only, and exempts only the mark's own unit test, which stands a Map in for localStorage). Privy's SDK writes its own keys in this site's localStorage as soon as its window opens, before anyone logs in (seen on 2026-11-21: `privy:caid`, a client id; `privy:sent:<appId>:…`; `privy:connections`), and keeps its session there once someone is in; it also asks `explorer-api.walletconnect.com` for the wallet list every time the window opens, even for someone who goes on by email. None of that happens before the first "Log in" or action, or the idle restore of a marked browser. On a later visit with the mark, Privy's code loads once the page is idle and lets the person back in without a window; if Privy finds no session, the mark is removed. Without the mark nothing of Privy loads: a first load of `/` contacted only the site itself, and the chunks of Privy's SDK are reached only through `privy-host-*.js` (`tests/vercel.test.ts`, `tests/bundle/build.test.ts`, `tests/bundle/audit.ts privySdkFiles`).
- Privy's own confirmation windows follow the lens. Decided by the owner on 2026-11-21 (`docs/defaults.md`, question 10 and D-21): they show with the lens on only. With the lens on (the footer's magnifier switch, or `?`), an account Privy keeps shows Privy's own window for every signature (a Give, a shake, the keys message) and every transaction, after the app's own review step, so a person who checks sees what is signed in Privy's words. With the lens off it shows none, and the app's review step and progress rail are the confirmation; so that such an account still sees what it confirms, the give screen's agreement keeps the contract and the hand's number in the calm view for it. A crypto wallet logged in through Privy shows its own window for every request either way. How: `apps/hand/src/wallet/privy-host.tsx` sets Privy's `embeddedWallets.showWalletUIs` to the lens, and its `Host` gives Privy the settings again on every flip (`lookKey` and `watchLook` include the lens, as they do the theme and the language), with Privy left mounted and the session kept (`privy-host.test.ts`, "a flip of the lens reaches Privy"). Privy 3.51.3 reads that setting as each request comes (`isHeadlessSigning`, through the wallet provider's handlers, which always call Privy's latest ones); requests through the wallet's EIP-1193 provider, which the app uses, carry no per-request `uiOptions`, so the setting is the only switch. Privy reports each set of settings it has not seen on this device once to its own analytics (`sdk_initialize`), the lens's as the theme's. Closing Privy's window answers 4001, which the app reads as "no", as for any wallet. With the lens on, Privy's transaction window does more than ask: once the person confirms, it waits for the transaction to be mined, shows "Transaction complete", and hands the hash back to the app only when the person presses "All Done" or closes it; until then the app's progress rail stays on "asking" (`wallet/send.ts`), and in a raise with an approve first Privy waits for the approve's receipt and then the app waits again. Nothing is lost meanwhile: the send's intent (nonce and block) is kept before the wallet is asked, and a resume settles it by nonce. That wait cannot be turned off from the app, since the EIP-1193 path takes no `uiOptions`. Also with the lens on, an account with some ETH but too little for gas gets Privy's "missing funds" view, whose button stays disabled (Privy's funding is not on); closing it answers 4001, so the app says "you said no" rather than naming the funds (the raise screen's own check refuses only a zero balance); with the lens off the same send fails as insufficient funds. Not yet seen in a browser: no real login has been done.
- Wallets listed: `detected_ethereum_wallets`, `metamask`, `rainbow`, `zerion`, `uniswap`, `wallet_connect` (well-known names before WalletConnect's alphabetical list of hundreds). Not Coinbase's own SDK (`coinbase_wallet`, `base_account`): its smart wallet opens a pop-up that the app's `Cross-Origin-Opener-Policy: same-origin` would cut off; its extension is announced by EIP-6963 anyway (Coinbase's relay is still allowed in `connect-src`, as Privy's page requires). WalletConnect runs on Privy's default project id unless the owner sets one in Privy's dashboard.
- The window follows the page: Privy's light theme (white, the app's own card colour) in light, or the app's dark card (`SURFACE_DARK_HEX`) in dark, read again when the theme flips; the app's amber (`AMBER_HEX`) as accent; the aHand lockup (`/ahand-logo-light.svg`, `/ahand-logo-dark.svg`); in Russian its title, the line under the logo and its wallet screens (`intl.textLocalization`, which Privy marks experimental). The rest of Privy's window (the email field's "Submit", "Other socials", "Continue with a wallet", "I have a passkey", the code screen) stays in English: `textLocalization` has no keys for them in 3.51.3. The Russian line under the logo (capped by Privy at 100 characters) names the ways in and says the buttons below are in English.
- Configuration: `"privy": { "appId": "…", "origins": […] }` (public; it ships in every page). `origins` is the list of site addresses the app expects Privy's dashboard to allow, and only for its own check: `https://ahand.in`, `https://*.ahand.in` and `http://localhost:` 3000, 3001, 3300, 3400, 3411 and 5173 (the ports let the public build be served on this machine). It is not the dashboard's list: on 2026-11-21 Privy's frame named, in its `frame-ancestors`, also `https://*.ahand.social`, `https://ahand.social`, `https://ahand-git-develop-gethering.vercel.app`, `https://welcome-primate-specially.ngrok-free.app` and `https://localhost:3411`. Whatever this app does with Privy's confirmation windows, a page on any allowed domain sets its own and can have a person log in and sign with Privy's wallet without a window, so the dashboard's list is the boundary that counts (the owner's step in [public-test-deployment.md](public-test-deployment.md#privys-dashboard) and question 10 in [defaults.md](defaults.md)). On any other site address the app's own sheet says at once "Logging in can't be reached right now…" and offers the browser's wallets, because Privy would still open its window there and fail only after the person typed their email (its key frame is refused by its `frame-ancestors`); measured on `http://127.0.0.1:3300`: the sheet in 0.5 s, no request to Privy. `base-sepolia.json` has it; the local stand's configurations do not (Privy's wallets cannot reach a local chain, and `parseConfig` refuses the pair). The build defines `__AHAND_PRIVY__` from it: without `privy` no Privy code is emitted, and the stand keeps the app's own sheet with its dev accounts and the browser's wallets.
- viem: the root `overrides` pin viem 2.52.0 for the whole tree, while `@privy-io/react-auth` 3.51.3 pins 2.57.8 and its subpackages ask for `^2.57.8`, so Privy's code runs on the older viem. The build and the window work; Privy's own signing and sending (`eth_signTypedData_v4`, `eth_sendTransaction`, `wallet_switchEthereumChain` inside its provider) have not run against it, since no real login has been done. Run one before relying on it.
- Privy unreachable: offline, at once; blocked or not answering, after 8 s (`READY_MS`; Privy was seen ready 1.3 to 2.5 s after the press); a site address outside `privy.origins`, at once. Closing Privy's window is "no": the app is as it was.
